## 一、核心知识点

### 📌 知识点 1：Agent 的最小工程公式与「边界」

```
Agent = LLM + 上下文 + 工具      （工程实现视角）
      = 大脑  + 眼睛  + 手脚      （直觉视角）

Agent = Model + Harness                    （生产形态视角）
Harness = 上下文管理 + 工具接口 + 约束 + 验证 + 纠正
Agent ↔ Environment                        （闭环交互，环境在 Agent 之外）
```

三个边界判断：

1. **公式不含 Environment**——环境是 Agent 交互的另一方，不是组成部分。
2. **Harness = Agent 边界内、模型之外**的运行与治理层。关键在于：**物理部署位置不能决定概念归属**——即使仿真环境和 Agent 跑在同一进程里，它仍然是 Environment。
3. **两个公式不是两套骨架**。`Agent = LLM + 上下文 + 工具` 才是全书唯一结构骨架（二至六章构建、七至九章评估进化、十章协作）；`Model + Harness` 只是「构建」部分在生产形态下的**内部观察视角**，把「上下文 + 工具」细分成了五项职责。

> ⚠️ `Model + Harness` 并非覆盖全书的目录。

**三组件 → 学术概念的映射**（有映射，但不严格等同）：

| 直觉 | 实现组件   | 学术概念      | 含义               |
| :- | :----- | :-------- | :--------------- |
| 大脑 | LLM    | 策略 Policy | 从可选行动中挑出最合适的     |
| 眼睛 | 上下文构造  | 观察与历史     | 把观察+历史组织成决策所需信息  |
| 手脚 | 工具与适配器 | 观察/行动接口   | 规定能读什么、能发什么、什么格式 |

一点需要区分的是：上下文 **≠** 整个观察空间；工具背后的对象仍属于环境。

### 📌 知识点 2：观察空间与动作空间——被低估的能力杠杆

本章工程价值最高的一条判断：

> **在底层模型固定时，提升 Agent 表现最主要的系统工程手段，往往就是重新定义或扩展观察空间与动作空间**（即扩展上下文和工具）。

- 没有通过观察通道进入上下文的信息，对模型**就像不存在**；
- 没有被动作接口允许的操作，模型**只能停在文字建议上**；
- 许多看似需要「更聪明模型」的问题，其实**只是接口问题**。

**两个佐证案例**：

| 产品           | 做了什么                                                                                   | 本质                           |
| :----------- | :------------------------------------------------------------------------------------- | :--------------------------- |
| **Manus**    | 把 Deep Research / Coding / Computer Use 三条独立路线的观察与动作空间**取并集**（虚拟浏览器 + 文件系统 + 代码/命令行执行） | 不是靠换更强模型变成通用 Agent，而是靠扩大接口边界 |
| **OpenClaw** | 把接口延伸到用户数字生活：二十余种消息渠道 + 本地 Gateway 连接 Google Drive / Notion / 本地文件系统                   | 本地优先，跨越了比云沙盒更大的数据边界          |

> 印证：Manus 后来补上了 Google Drive 连接器和桌面端本地访问——**产品能力的演进，往往就是观察空间与动作空间的演进**。

### 📌 知识点 3：工具（手脚）——五类分法与设计原则

**五类工具**（按 Agent 与外界互动的方向划分）：

| 类别         | 作用                      | 代表                          |
| :--------- | :---------------------- | :-------------------------- |
| **感知工具**   | 环境 → Agent 的观察          | 搜索引擎、文件系统、API/数据库           |
| **执行工具**   | Agent → 环境的行动           | 代码执行、文件操作、系统命令、外部 API       |
| **协作工具**   | 与其他 Agent / 人类协作        | 委托子 Agent、请求人类确认、多 Agent 协调 |
| **事件触发工具** | **被动**：由外部输入驱动 Agent 启动 | 新邮件、定时点、Webhook 回调          |
| **用户沟通工具** | 主动与用户建立连接、传递信息          | 文字消息、语音通话、邮件                |

> 第 4 类的特殊性：**它不是 Agent 主动调用的**，而是外部输入驱动 Agent 开始执行；本质上也是 Environment 向 Agent 提供观察的通道，所以归入广义工具体系。

**工具调用（Tool Calling）四步闭环**（ReAct 的前身）：

```
① 声明工具（名称/用途/参数）→ ② 模型自主决定「要不要调/调哪个/传什么」
→ ③ 执行结果追加到上下文 → ④ 模型据此决定下一步
```

**工具设计的核心原则**：

> **通用基础能力用于组合与探索；专用工具用于约束高风险和强业务规则操作。**

围绕这条原则，本章还给出几点说明：

- 从**最窄能力起步**，随复杂度提升再扩展：四则运算 → 一个计算器就够；读表清洗统计绘图 → 受限 Python 代码解释器比堆专用工具更好组合。
- 但**通用性也扩大出错与攻击面**：代码必须在隔离沙盒运行，默认禁网、不能读授权目录外文件，并对执行时间/CPU/内存/输出大小设上限。长程任务用**受控虚拟工作目录**（限定读写路径、容量、文件类型，防路径越界），而不是暴露宿主文件系统。
- **高风险操作**（支付、删数据、发邮件、生产部署）仍应封装为参数明确、权限受限、全程可审计的**专用工具**，必要时加预览与人工确认。
- MCP 标准的推广正在让工具接入变容易。
- 工具设计质量直接决定 Agent 能走多远：**接口不清晰 → 模型乱用；错误处理不到位 → 死锁；权限太宽 → 后果难挽回**。

### 📌 知识点 4：LLM（大脑）——内部思考、模型即 Agent、三条学习路径

**内部思考（internal thinking）是 LLM Agent 的独特能力**：行动前先规划推演，不改变外部环境却能显著提升行动质量。它之所以有效，是因为预训练习得了人类知识中沉淀的逻辑规则（数学定律、因果关系、问题分解策略）——**所以今天的 LLM Agent 不是盲目随机探索，而是在结构化知识体系上展开**。

**「模型即 Agent」（Model as Agent）**：先进模型通过后训练（尤其强化学习）把工具调用能力**内化**为原生能力——何时调用、调哪个、传什么参数都由模型自己决定，无需人工编排。

这里有个**容易混淆的点**，本章专门做了澄清：

| 归属                   | 内容                                                |
| :------------------- | :------------------------------------------------ |
| **强化学习写进参数的是「决策」**   | 何时调用工具、调哪个、传什么参数、拿到结果是否继续、如何串联上百次调用               |
| **工具本身与执行属于框架/托管服务** | `web_search` / `code_runner` 的真实实现、代码沙盒、调用发起与结果回传 |

> 所以「编排循环」并没有消失，而是**从客户端移到了服务端**，决策权交给了模型。（Kimi 通过 Formula 服务端脚本引擎运行官方工具。）

**Harness 一词的来源与寓意**：原指马具（缰绳与挽具）——**不是限制马的奔跑，而是把力量引到正确方向**。模型是强大但不可预测的马，Harness 是把能力引导成可靠任务执行的工程外壳。

**「模型变强，Harness 会不会被吃掉？」——本书的立场：方向认同，节奏务实**

- 依据是 Rich Sutton 的《苦涩的教训》：七十年 AI 研究反复上演——把人类先验编码进系统短期见效，长期总是输给能随算力数据扩展的通用方法（搜索与学习）。
- **方向上**不怀疑模型会持续吃掉 Harness（工具调用、长程规划都曾是外部编排，如今已是原生能力）；
- **节奏上**这个过程远比想象中慢：训练以月计，模型无法一次内化真实业务的所有约束与偏好。**模型此刻的能力边界，就是 Harness 此刻的价值所在**。
- 一句话概括：**模型还做不稳的，Harness 先补上；模型每内化一层，Harness 就卸下一层，转而兜底新的能力前沿。**

**Agent 的学习机制：三条互补路径**（按更新位置与持续时间分）

| 路径         | 发生位置                                     | 优势                  | 局限                 | 对应章节    |
| :--------- | :--------------------------------------- | :------------------ | :----------------- | :------ |
| **上下文适应**  | 当前任务内                                    | 快、低成本               | 受上下文窗口约束，不改变持久状态   | 第二章     |
| **外部产物更新** | 跨任务（知识文档 / Prompt / Skill / 程序与 Harness） | 可审计、可修订、可控积累        | 执行时仍需通过上下文或工具接口被使用 | 三～五章、九章 |
| **参数更新**   | 训练周期（后训练）                                | 泛化自然、能内化难以显式表达的高维能力 | 部署成本高              | 第八章     |

> 三者**不是互斥分类，而是不同时间尺度上的协同**：上下文负责临场适应，外部产物负责可控积累，参数负责内化难以言说的能力。  
> 这三条路径的排列顺序恰好对应**可回滚程度从高到低**（呼应设计模式「最小 diff + 可回滚」）。

### 📌 知识点 5：上下文（眼睛）——五组件构成与消融实验结论 ★★

**上下文的五个组成部分**：

| #  | 组件                          | 归类       | 说明                                                                    |
| :- | :-------------------------- | :------- | :-------------------------------------------------------------------- |
| 1  | **系统提示词** System Prompt     | **静态前缀** | 开发者编写、全程不变，Agent 的「岗位说明书」；内含用户记忆与环境状态                                 |
| 2  | **工具定义** Tool Definitions   | **静态前缀** | 工具名称/描述/参数格式；**没有它模型就无法识别和调用任何工具**                                    |
| 3  | **用户消息** User Messages      | 动态轨迹     | 用户输入，可能含 RAG 检索引入的外部知识                                                |
| 4  | **模型回复** Assistant Messages | 动态轨迹     | 最多含三部分：`reasoning`（思考）+ `content`（回复）+ `tool_calls`（行动），一次回复中三者不必同时出现 |
| 5  | **工具执行结果** Tool Results     | 动态轨迹     | 下一步思考的直接依据，让 Agent 从结果中学习、避免重复犯错                                      |

> ⭐ **Agent 的上下文 = 静态前缀（1+2） + 轨迹（3+4+5）**  
> 静态前缀保持稳定（关乎 KV Cache 性能），轨迹随交互不断增长。

#### 实验 1-1 ★★：上下文消融实验

**方法**：消融研究（Ablation Study）——像医生逐一排除病因，去掉 A 看是否正常、再去掉 B，以此判断每个组件的贡献。

**设计**：五个组件中**系统提示词不参与消融**（没有它 Agent 连基本角色认知都没有，测试没有意义），故为 1 组完整基线 + 4 组各缺一个组件：

| 组别              | 移除的组件            |
| :-------------- | :--------------- |
| full            | 无（基线）            |
| no_history      | 历史消息             |
| no_reasoning    | 思考过程 `reasoning` |
| no_tool_calls   | 工具定义             |
| no_tool_results | 工具执行结果           |

**结论（按重要性排序）**：

| 组件                 | 作用            | 缺失后果                                                                                                                                   |
| :----------------- | :------------ | :------------------------------------------------------------------------------------------------------------------------------------- |
| **工具定义**           | Agent 行动能力的基础 | 无法调用任何工具。**但失去行动能力 ≠ 沉默**——模型照样给出一份格式工整、语气笃定的答案，数据却来自参数记忆，**与真正基于观测的答案排版一模一样**。是坦白拒绝还是就地编造，主要取决于模型自身的幻觉率与诚实度；「不得自行估计」这类提示约束只能降低概率、不能消除 |
| **工具执行结果**         | 闭环控制的关键       | Agent「盲目」执行，反复重试直到耗尽迭代预算                                                                                                               |
| **思考过程 reasoning** | 记录「为什么这么做」    | 当它**能从工具结果重建**时，丢掉几乎没有代价                                                                                                               |
| **历史消息**           | 防止冗余操作        | 重复犯同样的错误、重复调工具                                                                                                                         |

**核心洞察**：

1. **上下文决定了 Agent 能看到什么，而 Agent 只能基于它看到的信息做决策。**
2. **组件并不等价**——衡量标准是**它承载的信息能否从别处重建**。
3. 「每个组件都不可或缺」这类论断**要靠实测**，而且模型迭代很快，同一消融换到新模型完全可能得出不同结论。
4. **「给出了回答」不等于「完成了任务」**。上下文残缺时典型的失败不是报错退出，而是**一个看上去毫无破绽的答案**。

### 📌 知识点 6：ReAct 循环——三者如何协同

**ReAct = Reasoning + Acting**，但实际循环是**三个环节**：

```
思考（想做什么）→ 行动（调用工具）→ 观察（看返回结果）→ 继续思考……
```

**最小运行骨架**（机制示意：Model 只决定下一步，Harness 组装上下文/校验/执行，Environment 产生真实状态变化）：

```python
trajectory = [user_request]
repeat:
    context  = stable_prefix + trajectory
    decision = Model(context)
    trajectory.append(decision)

    if decision has no tool call:
        return decision.answer

    for call in decision.tool_calls:      # 独立调用可并行
        validated_call = Harness.validate(call)
        observation    = Environment.execute(validated_call)
        trajectory.append(observation)
```

**轨迹（trajectory）** = 执行过程中不断积累的消息历史。它有个重要性质：

> **轨迹结构化 → 系统易解释、易调试**；分析大量轨迹还能发现行为模式、优化决策路径、改进工具设计，甚至沉淀进知识库或用于强化学习训练，形成**从经验中学习的闭环**。

书中的多币种汇总案例：**3 次迭代、4 次工具调用**就完成了任务（换汇 ×3 → 代码汇总 ×1 → 给出最终答案）。

### 📌 知识点 7：Harness 五要素——生产系统的竞争核心

**演进逻辑**：最小 Demo 只需 Model + 能构造上下文、暴露工具的 Harness；但 Demo 与可靠产品之间有巨大鸿沟（幻觉、选错工具、不会自我恢复），**生产系统必须在同一边界内加上约束、验证、纠正**。

| 要素               | 职责与核心原则                                                             | 实际例子                             | 详见   |
| :--------------- | :------------------------------------------------------------------ | :------------------------------- | :--- |
| **Context 上下文**  | 提供感知信息；**信息要充分**，让每个决策点都有足够信息                                       | 系统提示词、知识库、Agent 状态栏、Sidecar 旁路查询 | 二、三章 |
| **Tools 工具接口**   | 提供观察与行动手段；**接口要清晰**，命名直观、参数有例子、边界有说明                                | MCP 工具、代码解释器、搜索工具                | 四章   |
| **Constrain 约束** | 设定行为边界；**故障安全默认值**——所有能力默认关闭，必须显式开放（类比手机 App 权限）                    | Claude Code 中每个工具默认需用户授权         | 四章   |
| **Verify 验证**    | 自动判断结果对错；**只看结构化数据**（如工具返回的 JSON 字段），**不看模型自由生成的文本**，因为后者可能已被提示注入操纵 | Linter、类型系统、工具调用结果校验             | 五、六章 |
| **Correct 纠正**   | 自动修正或回退；**确认无法恢复前不暴露中间态**（先静默重试，不把半成品给用户）                           | 静默重试、接续生成、连续失败熔断回退人工             | 二、五章 |

**五要素构成闭环**：上下文 + 工具让 Agent「**能做事**」；约束预防错误、验证发现偏差、纠正形成闭环，共同让 Agent「**不做错事**」。

> ⭐ 一处不对称性：**早期框架重心在「上下文 + 工具」，生产级系统的重心已转向「约束 + 验证 + 纠正」。**  
> 证据：Claude Code 的 Harness 中**绝大部分代码都是约束、验证与纠正**，工具本身只是小一部分。其保障机制包括：流程状态管理、多层上下文压缩、权限分类、**熔断器**（Circuit Breaker，连续错误自动断电，类比保险丝跳闸）、错误恢复机制。

**一句话结论**：**行业正在从「能做事」向「可靠地做事」转变，Harness 工程因此成为 Agent 系统的核心竞争力。**

### 📌 知识点 8：工程范式的五波演进

| 波次 | 名称                                          | 关注范围                                                               |
| :- | :------------------------------------------ | :----------------------------------------------------------------- |
| 1  | **提示工程** Prompt Engineering                 | 优化输入给模型的自然语言指令                                                     |
| 2  | **上下文工程** Context Engineering               | 系统性管理模型能看到的**所有信息**                                                |
| 3  | **Harness 工程**                              | 扩展到「Agent 如何组织模型运行并与环境交互」：上下文与工具接口、约束、验证、反馈循环、错误恢复                 |
| 4  | **Loop 工程** Loop Engineering                | 从单次运行扩展到**跨轮次的持续自主运转**：谁发现下一件事、何时验证、何时才算真正完成（第十章）                  |
| 5  | **Graph 工程** Graph Engineering（2026.07 起流行） | 把 Agent 循环、确定性程序、人工审批组织成**显式执行图**：节点=能力，边=路由与依赖，结构化状态沿边传递并在关键边界持久化 |

> ⭐ **关键关系：这五个阶段不是替代，而是层层包含**——提示工程 ⊂ 上下文工程 ⊂ Harness 工程 ⊂ Loop 工程 ⊂ Graph 工程（单个 Agent 循环正是执行图中的一个节点）。  
> 由此推出的判断是：**当各家模型能力越来越接近、不再是决定性差异因素时，竞争优势就转移到了模型之外的工程实践。**

**有力例证**：LangChain 在 Terminal Bench 2.0 上得分从 **52.8% → 66.5%**（排行榜 30 名开外 → 前 5），**模型没变，只改了 Harness**（让 Agent 自动检查执行结果、检测重复循环、优化思考策略）。

**Anthropic 的三条核心原则**：

| 原则               | 含义                                                                                                                                                           |
| :--------------- | :----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **保持简单**         | 从最简单方案开始，只在必要时加复杂度。直接 API 调用 > 复杂框架；清晰代码 > 聪明抽象。**每多一层抽象，都是以后调试的新盲区**                                                                                        |
| **保持透明**         | 明确显示规划步骤、执行日志、决策轨迹。不只是为调试，也是**用户建立信任的前提**——黑箱里的错误，外部观察者既无法定位也无法纠正                                                                                            |
| **设计好工具接口（ACI）** | 从 **Agent 视角**设计接口（而非程序员视角）。命名与参数直观，易错处从设计上让错误无法发生——SIM 卡缺角、微波炉门没关好绝不加热。这种「用设计消除错误」的思路在制造业叫**防呆（Poka-yoke）**，源自丰田。**模型与工具之间唯一的沟通通道就是接口本身，模糊的接口会被模型放大成系统性错误** |

### 📌 知识点 9：模型选型与编排模式

**模型选型：五个考量**

1. **闭源 vs 开源**：闭源能力领先但贵、受 API 策略限制；开源差距约 6 个月内、可私有化/可微调，适合成本敏感或数据合规场景。国内 Agent 能力较强：DeepSeek、Kimi、GLM。  
   → 本章强调**不要只看排行榜，要在自己的任务上评估**（第七章）。
2. **策略边界**：模型在基准上具备某能力 ≠ 承载它的产品允许使用者调用。不同厂商对网络安全、模型蒸馏、模型提取、隐私数据、高风险操作设不同边界；同一任务在聊天产品 / Coding Agent / API 中结果可能不同。选型不只看准确率、价格、速度，还要测**模型是否愿意执行、接口是否暴露所需能力、服务条款是否允许**。业务关键任务要准备人工接管或合规替代模型。
3. **绝大多数 Agent 需要支持思考（Reasoning）的模型**：多步思考、工具选择都依赖它。仅极少数例外（单步简单任务、Computer Use 中固定位置的简单点击）。
4. **输出 token 速度**：直接决定端到端延迟——**20 轮推理、每轮慢 2 秒 = 总共多等 40 秒**。
5. **多模态能力**：需理解图片/音频/视频时是硬性要求，模型间差异很大。

**编排模式：工作流 vs 自主 Agent**

> 核心原则是**从简单到复杂**——先考虑单个 LLM 调用；能用优化提示词解决就不引入 Agent 系统；可清晰分解为固定子任务的多步处理用工作流；**只有需要动态决策和灵活执行路径时才用自主 Agent**。书中同时指出：**Agent 系统通常用延迟和成本换取更好的任务性能**，这种交换需要谨慎权衡。

| 维度     | 工作流 Workflow                                                              | 自主 Agent                                             |
| :----- | :------------------------------------------------------------------------ | :--------------------------------------------------- |
| 执行路径   | **预定义、确定性**，代码写死                                                          | **运行时根据环境反馈实时决定**                                    |
| LLM 角色 | 只在节点内部负责理解与生成                                                             | 自主规划步骤、识别失败、调整策略                                     |
| 优势     | ①**严格流程控制**（「付款前不能预订」由代码强制，不依赖 LLM 判断）②**安全性**（攻击面被限制在单个节点内，提示注入最多影响当前节点） | 能应对开放式、步骤数难预测的问题                                     |
| 局限     | **缺乏变通性**，预设外的情况只能走异常分支或交还人类                                              | 更高成本、**复合错误风险**；需明确**停止条件**（任务完成/最大迭代/不可恢复错误），否则易死循环 |
| 典型场景   | 固定子任务流程、文生图                                                               | Coding Agent（SWE-bench）、Computer Use、迭代搜索分析          |

**混合方式**：① 关键合规流程用工作流 + 灵活部分切自主（如 n8n 同一系统内混用两类节点）；② **先由自主 Agent 把工作流写出来、再由工作流执行**——Agent 决定拓扑并生成编排代码，代码一旦生成执行阶段就退回确定性。既保留面对未知任务的灵活性，又不必让模型参与每次调度（第十章详述）。

**关于「适配层」的洞察**（本章最有穿透力的观点之一）：

> 文生图工作流里的「提示词改写」节点，本质是在**给工具的能力短板打补丁**——它存在的原因是文生图模型「听不懂人话」，LLM 做的是**翻译**。  
> 而**换成具备原生图像生成能力的多模态模型（Nano Banana 2、GPT-Image 2），这个节点就不需要了**。

由此推广：**Harness 里那些给模型能力短板打补丁的部分，会随着模型变强被模型自己内化。** 仅在第一章，这样的事就发生了好几轮：

| 曾经的 Harness 补丁              | 被什么内化          |
| :-------------------------- | :------------- |
| few-shot 示例、「让我们一步一步思考」提示技巧 | 指令微调 + 推理模型    |
| 输出格式修复、JSON 解析容错            | 结构化输出 + 原生工具调用 |
| 文生图的提示词改写                   | 原生多模态理解与生成     |


> **每一轮内化，消灭的都是「翻译」和「脚手架」这类适配层代码。**

**反面教材**：一开始就构建复杂工作流/多 Agent 系统。例如「从百万条聊天记录提炼个人记忆」，很容易画出一条看似严谨的流水线（切分→提取→证据核验→身份解析→整理→合并复核，再建事实图/覆盖账本/不可变版本），每个部件单看都有道理，**组合起来却非常低效不可靠**——因为复杂工作流的执行拓扑固定，遇到新例外只会继续加节点，架构越来越复杂、通用性越来越差，**模型本可依据上下文的语义判断反而被写死**。

> 由此得出的结论：**Harness 很重要 ≠ Harness 越复杂越好**。  
> Manus 用 **"Less structure, more intelligence."** 概括这种取舍：给能力强足够的 Agent 清晰目标 + 必要上下文 + 可组合工具，用自然语言告诉它如何查证、比较、处理冲突；程序只固化必须始终成立的边界（权限、不得覆盖原始材料、原子发布）。**只有业务约束要求，或评估反复暴露某类稳定失败时，才把步骤升级为专门的验证器、独立 Agent 或确定性流程。**  
> **好的结构不是替 Agent 预演全部思考，而是守住边界，并把边界内的决策空间还给模型。**

**主流框架速览**：

| 框架                    | 定位                                           | 编排模式        |
| :-------------------- | :------------------------------------------- | :---------- |
| Codex Harness         | Codex 的开源运行时（exec / SDK / app-server 三条集成路径） | 自主          |
| Claude Agent SDK      | 生产级开发框架（Harness 实现本身不开源）                     | 自主          |
| LangChain / LangGraph | 通用 LLM 应用框架                                  | 工作流 + 自主    |
| n8n                   | 可视化工作流自动化                                    | 工作流 + 自主    |
| Dify                  | LLM 应用开发平台                                   | 工作流 + 对话式   |
| CrewAI                | 角色化多 Agent 编排                                | Multi-Agent |
| OpenClaw              | 开源全能个人 Agent                                 | 自主 + 事件驱动   |
| DeepSeek Harness / Pi | Agent 自进化 / 极简 Coding                        | 插件化 / 自主    |

> 选框架的关键不是它多复杂，而是它能否用尽可能少的抽象层让人专注于业务逻辑。框架发展极快，具体框架的用法不构成长期价值。

### 📌 知识点 10：护栏与安全性——三层防线

**组织逻辑**：三层不是按**请求处理的先后顺序**排的，而是按**被绕过的难度**排的——**越靠下的层越不依赖模型自己的判断，因此越难被一次成功的攻击穿透**。全书的安全讨论都挂在这棵树上。

| 层        | 管什么                   | 机制                                                                                                                | 代表                                       |
| :------- | :-------------------- | :---------------------------------------------------------------------------------------------------------------- | :--------------------------------------- |
| **上下文层** | 模型**能看到什么**（进入上下文前拦截） | ① 相关性分类器（标记偏题）② 安全分类器（检测越狱 / 提示注入）③ 内容审核 ④ 基于规则的保护（黑名单、长度限制、正则）＋ 来源标注与「指令/数据」分离                                   | Anthropic **Constitutional Classifiers** |
| **执行层**  | 模型**能做什么**（动作生效前验证）   | **工具风险评级**（按可逆性/权限等级/财务影响标注低中高，高风险需额外审查或人工确认）；复核必须由**上下文之外**的机制完成（独立审查进程、最小权限凭证、沙盒隔离、人在回路）；**输出检查**（PII 过滤器、输出验证） | —                                        |
| **数据层**  | **世界最终能被改成什么样**       | 把「谁能对哪条数据做什么」交给稳定、经人类审查的机制强制执行：数据库行级安全策略、约束与校验器、受控视图与存储过程、受信任运行时绑定的访问上下文                                          | —                                        |

**两个关键区分**：

- **越狱 vs 提示注入**：越狱是**用户自己**试图绕过模型安全限制；提示注入是**攻击者通过外部数据（网页内容、文档）间接**操纵模型行为。
- **上下文层的结构性上限**：**处在同一个上下文里的 Agent，很难判断自己是否已经被注入**。所以上下文层只能降低攻击成功率、给不出保证——这正是必须有下面两层的原因。（这也是设计模式「提议者—审核者」成立的前提之一。）

**Constitutional Classifiers 的三个机制**（工业级实践）：

1. **规则驱动**：用自然语言写成规则 → 生成合成训练数据 → 训练输入输出分类器。
2. **上下文联合判断**：把提问和回答**放在一起**检查——有些回答单独看毫无问题（如「如何使用食品调味料」），只有对照提问才能发现「食品调味料」其实是化学试剂的暗语。
3. **两级筛查**：先用极轻量探针（直接读模型内部激活，几乎零成本）扫全部对话，可疑再交强分类器复审，而非直接拒绝。**第一级即使误报多也不影响体验，成本大幅降低。**

**容易被忽略的失败模式：误拒绝**。为降低危险请求放行率，模型可能连合法但形式敏感的任务也拒（如经授权的安全测试、模型蒸馏研究）。**因此护栏评估不能只测「该拒的是否被拦」，还要测「明确允许的是否能正常完成」。**

**人工干预（Human in the loop）的两个触发条件**：

1. **超过失败阈值**——为重试/操作次数设上限，超限即升级人工；
2. **高风险操作**——敏感、不可逆或高风险操作（典型：授权大额退款或付款）应触发监督，至少在团队对可靠性建立足够信心之前如此。

这在部署早期尤为重要：有助于识别失败模式、发现边缘情况、建立健壮的评估周期。

### 📌 知识点 11：五个贯穿全书的设计模式 ⭐

| 模式                                              | 定义                                                                      | 为什么成立                                          | 在哪些章出现                                                                                        |

## 二、用自己的话简明总结

第一，**Agent 就是给大模型装上眼睛和手脚，并围上一圈保险**。「LLM + 上下文 + 工具」是它的骨架，其中真正决定 Agent 能干什么的，不是模型有多聪明，而是**信息能不能进来、操作能不能出去**——所以当模型固定时，扩大接口边界（更多观察、更多动作）往往就是最有效的提升手段，Manus 和 OpenClaw 的演进史就是不断扩张这两类空间的历史。

第二，**Agent 的每一次决策，只依赖它此刻能看到的东西**。这个「能看到的东西」就是上下文，由不变的静态前缀（系统提示词 + 工具定义）和不断变长的轨迹（用户消息 + 模型回复 + 工具结果）拼成。消融实验最有价值的发现不是「每个组件都重要」，而是**组件之间并不等价**——判断标准是「它承载的信息能否从别处重建」。丢掉工具定义或工具结果，会直接夺走行动能力与闭环能力；而丢掉思考过程，只要它能从工具结果里重建，代价就很小。

第三，也是最反直觉的一点：**失败的样子往往不是崩溃，而是一个看起来毫无破绽的答案**。没有工具定义的模型不会沉默，它会用记忆里的汇率给出一个排版漂亮、语气笃定的错误结论。这直接解释了为什么「能跑通 Demo」和「能上生产」之间隔着巨大鸿沟，也解释了为什么生产的 Harness 里绝大部分代码不是「让它能做事」，而是「让它别做错事」——约束、验证、纠正才是重心所在。

第四，**五个范式是层层套娃，不是互相取代**：提示工程 ⊂ 上下文工程 ⊂ Harness 工程 ⊂ Loop 工程 ⊂ Graph 工程。这个包含关系本身就说明了一件事——**当模型能力趋于接近、不再是差异化因素时，胜负就落在模型之外的工程实践上**。LangChain 在 Terminal Bench 上不动模型、只改 Harness 就把成绩从 52.8% 拉到 66.5%，是这句话最直接的证据。

第五，**「模型越强，Harness 越不重要」是个误读；正确的关系是「模型越强，Harness 的形态在变」**。文生图工作流里那个把「人话」翻译成 SD 提示词的改写节点，换成原生多模态模型后整段就消失了——Harness 里给模型短板打补丁的部分确实会被吃掉，但每吃掉一层，模型的自主决策空间就扩大一层，出错的影响面也随之扩大，于是又需要新的约束、验证与纠正。所以 Harness 不是对抗《苦涩的教训》，而是这个教训在工程时间尺度上的实践。

第六，**工程顺序是「先简单，再复杂」**：先试单次 LLM 调用 → 再试固定工作流 → 最后才上自主 Agent。因为自主性是用延迟和成本换性能，而且会引入复合错误。Manus 那句 "Less structure, more intelligence." 讲的是同一件事——**好的结构不是替 Agent 预演全部思考，而是守住边界，把边界内的决策空间还给模型**。

## 三、我的理解与主要收获

### 🎯 三个最值得迁移到实际项目里的判断

**1. 「接口问题」容易被误判成「模型问题」**

本章给出的排查顺序是：先问「完成任务所需的数据进上下文了吗」「完成任务所需的操作被封装成工具了吗」，再考虑换模型或调提示词。工具层复算的那组数字（合计 9,602,895.73、均值 2,400,723.93）说明了这一点——任务本身毫无智力难度，需要的只是「能换汇 + 能算数」这两个动作接口。**很多所谓的智能问题，本质是接口没铺好。**

**2. 「完成 ≠ 正确」——groundedness（可依据性）是独立于正确性的指标**

实验中「移除工具定义」那一组会产出一个**格式完美、数字错误、且与正确回答排版无法区分**的结果。由此有三点：

- 只看「有没有输出」「有没有报错」的监控是**无效监控**；
- 要像实验 1-1 那样，**用「这个消息里是否声称了模型未被给予的数字」来判断答案是否有依据**，而不是只看它对不对；
- **可依据性与正确性是两条独立的轴**——没有观测却报出正确总数的模型，同样不算「读到」了。

对要交付给业务方的 AI 产物，这一点同样成立：**区分「算出来的」和「想出来的」，比任何提示词技巧都更重要。**

**3. 提示词的约束只是概率偏移，不是开关**

实验中那句「不要自行估计汇率，请使用工具观测」，在带约束任务下同一模型仍有 2/13 组报出无依据数字；去掉这句，同一模型立刻给出与工具汇率表相差仅 0.16% 的自造数字，还附了一句「基于所假设汇率」的说明——**只看总数的读者根本不会注意到**。这说明「用提示词做安全兜底」并不可靠：**提示词能降低概率，不能提供保证；能提供保证的是结构化的机制（验证只看结构化数据、数据层强制约束）。**

### 🧭 几点延伸认识

- **概念归属由职责决定，不由部署位置决定**：书里那句「即使仿真环境和 Agent 跑在同一进程，它仍然是 Environment」提供了一个很干净的架构分层方法——先分清哪些属于 Agent 内部（Harness）、哪些属于被操作的环境。
- **接口设计要主动让错误无法发生**：模型和工具之间唯一的通道就是接口本身，模糊的接口会被模型放大成系统性错误。这与数据处理中「列名要清晰、字段要自解释」同源，但要求更严——不能靠文档提醒。
- **「只增不改」和「最小 diff + 可回滚」是可复用的通用纪律**：前者关系到 KV Cache 前缀稳定性的性能含义（**改动越靠前，作废的缓存越多**），后者是让修改可归因的前提。
- **过度设计的判断标准**：不是「多一个节点看起来很严谨」，而是「业务约束是否要求」以及「评估是否反复暴露同一类稳定失败」。反例里那条「从百万条聊天记录提炼个人记忆」的流水线很典型——每个部件单看都对，组合起来非常低效。
